# Apply host commands at render-block boundaries

Status: accepted prototype contract, 2026-10-24; exact sample-position scheduling is deferred.

The render stream drives one authoritative engine. At the beginning of each render block, the audio thread establishes a cutoff and takes a bounded batch of commands that were already published by that cutoff. Commands arriving after the cutoff wait for a later block. Commands apply in FIFO order at the block boundary; no exact sample-position scheduling is promised. Bound both queue capacity and per-block command work. If admission fails, return an explicit overload/rejection; never silently discard a critical command. An accepted command may be deferred by backlog or the work budget, so it is not promised to apply in the next block.

Every command has an ID and session generation. Report queue acceptance separately from engine application, with the actual application generation, render block sequence, and rendered frame. Interruption/restart advances the generation. Host-detected capture loss/device failure is handled before ordinary queued commands at the next safe boundary; pending commands from the old generation become stale and cannot restart capture without a new explicit user action. Lifecycle work, device negotiation, allocation and file operations remain outside the render callback; only bounded real-time-safe engine mutations execute at the boundary.

Preserve FIFO among accepted commands that survive adapter staging. In the Windows adapter's bounded staging queue, coalesce only consecutive pending absolute track-gain assignments for the same track or master-gain assignments for master scope. The parameter key is `(scope, track ID when applicable)`. A different parameter, transport/lifecycle command, session replacement, or generation change ends the run. Coalescing may replace only a command still in adapter staging; once handed to the audio-thread queue, it is immutable and retains FIFO position. Give every command an ID; when a pending command is replaced, explicitly report it as superseded by the replacement ID, and never report it as applied. Only report application when the surviving assignment reaches the engine. Bound staging, audio queue and acknowledgement delivery; reject admission explicitly if capacity is unavailable, including when a terminal acknowledgement cannot be retained. Flush at a bounded cadence so a continuously moving slider still updates audio responsively; do not debounce indefinitely. This queue policy does not imply gain smoothing or alter engine semantics: track and master gain assignments remain immediate on Web and Windows, while existing sample-counted FX transition ramps remain in the portable engine. If measurements or listening reveal gain artifacts, evaluate smoothing as a separate cross-platform requirement. Validate coalescing runs, barriers, immutable handoff, overload, and superseded-versus-applied acknowledgements. The platform-neutral contract owns command semantics; this transport optimization belongs to the Windows adapter.
