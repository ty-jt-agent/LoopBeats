# Use explicit WASAPI control in the Windows prototype

Status: accepted, 2026-10-24; prototype decision, not a general backend commitment.

Build the narrow Windows audio host around explicit WASAPI shared-mode control so it can query the endpoint's supported shared periods and request a valid low period through `IAudioClient3`, while retaining regular shared mode as the availability fallback from [ADR-0005](0005-windows-shared-mode-audio-strategy.md). Use existing Rust bindings or `wasapi-rs` where they cover the required behavior and call the underlying Windows APIs where needed. Do not fork or extend CPAL merely to preserve a generic stream abstraction. Keep Windows dependencies, COM handling, period negotiation, and device lifecycle inside the Windows host; the portable LoopEngine and platform-neutral application contract have no WASAPI dependency.

Keep the experiment to event-driven capture and rendering, bounded buffering, the existing engine, one existing effect, and diagnostics. Initial support for separate capture and render endpoints, render-driven processing and bounded capture transfer is recorded in [ADR-0009](0009-separate-capture-and-render-endpoints.md); exact clock reconciliation remains open. Account for capture/render synchronization and buffering explicitly; a small render period alone does not establish low round-trip latency. Report requested and negotiated settings, fallback reason, and stream discontinuities. Validate complete microphone-to-output latency and stability before expanding the host. This decision is easy to discard if measurement shows the path is unsuitable and does not establish a general-purpose WASAPI wrapper requirement or prevent a later backend change.
