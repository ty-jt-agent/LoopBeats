# Windows application architecture

Status: architecture interview in progress. This document records confirmed direction; it is not an implementation specification or authorization to begin product work.

## Confirmed release scope

The first Windows release targets Windows 11 Home and Pro versions still supported by Microsoft at release time, x64 only. Windows 10 is outside the supported and tested scope, but no artificial compatibility blocker should be added if the application happens to run there. ARM64 requires a separate scope decision, build and hardware validation. Before release, record the exact minimum Windows version/build and the versions/builds actually tested, and recheck Microsoft's lifecycle information then. See [ADR-0007](../adr/0007-windows-release-support-policy.md).

Windows 11 does not guarantee that an audio endpoint or driver supports low-period shared WASAPI. The Windows host must query device capabilities, negotiate periods at runtime, report its actual configuration and retain the regular shared-mode fallback in [ADR-0005](../adr/0005-windows-shared-mode-audio-strategy.md).

## Current product boundary

Reuse the React/TypeScript interface inside a desktop WebView. The native Windows Rust host owns microphone capture, engine processing, monitoring, recording, playback, device management and audio lifecycle. The WebView is not a timing authority and does not use browser audio APIs for its live path. It communicates through a platform-neutral application contract using bounded commands and acknowledged state snapshots; live PCM never crosses the bridge. Keep the Web application working with its separate browser host and adapter. The shared Rust `LoopEngine` remains authoritative for transport, track behavior, mixing and effect state. See [ADR-0004](../adr/0004-platform-hosts-and-shared-engine.md).

The initial native prototype uses explicit event-driven WASAPI shared-mode control to query/request the lowest supported period through `IAudioClient3`, with an explicit regular shared-mode fallback. It must account for capture/render synchronization and buffering, expose requested and actual settings and fallback reasons, distinguish initialization failures, and report stream discontinuities. It supports separate capture and render endpoints, with render driving the engine and capture transferred through a preallocated bounded buffer. Validate a matched-device baseline, separate endpoints, and a sustained independently clocked pair; exact clock-reconciliation implementation remains open. Include built-in microphone with wired headphones and USB microphone with built-in wired output; Bluetooth is outside initial low-latency acceptance. Exclusive mode and ASIO are outside the prototype. Complete microphone-to-output latency and dropouts must be measured before expanding it. See [ADR-0005](../adr/0005-windows-shared-mode-audio-strategy.md), [ADR-0006](../adr/0006-explicit-wasapi-prototype.md), and [ADR-0009](../adr/0009-separate-capture-and-render-endpoints.md).

The host validates capture continuity before passing each affected block to LoopEngine. Confirmed sample loss during REC or overdub triggers `LoopEngine::interrupt()` at the earliest safe processing boundary, regardless of experimental warning thresholds; low occupancy, delayed callbacks, and normal resampling alone do not. When not recording, playback continues and missing monitoring input may be zero-filled or stale input discarded while a discontinuity is reported. The UI reports the session-wide result: transport reset, monitoring off, unfinished initial recording discarded, completed recordings retained, and any overdub retained only through already-written samples. The host records reason/details outside the callback and never auto-resumes capture. Acceptance includes focused initial-REC, overdub, and playback-only interruption cases with exact sample retention/discard outcomes. See [ADR-0010](../adr/0010-interrupt-on-capture-loss.md).

UI commands apply at render-block boundaries in FIFO order. The audio thread takes a bounded batch at a defined block-start cutoff; later arrivals wait for the next block. Commands carry IDs and session generations, with separate admission and application acknowledgements stamped by render block/frame. Bounded queue overflow is explicit; accepted work may wait behind backlog or the per-block budget. Interruption/restart advances generation and invalidates old pending commands before they can restart capture. The Windows adapter may coalesce consecutive pending absolute track/master gain assignments only while they remain in its bounded staging queue; replacement is acknowledged as superseded, and commands are immutable after handoff to the audio queue. A bounded flush cadence prevents indefinite slider delay. This optimization is Windows-specific and does not alter the shared UI contract. No exact sample-position scheduling is promised by the prototype. See [ADR-0011](../adr/0011-render-block-command-scheduling.md).

Track and master gain assignments remain immediate in the portable engine for both Web and Windows. Keep the existing sample-counted FX transition ramps. Parameter coalescing changes only which pending gain assignments reach the engine; it adds no interpolation or ramp and must not create platform-specific gain behavior. If measurements or listening reveal audible gain artifacts, evaluate smoothing as a separate cross-platform requirement.

## Portable sessions

Create a nonempty TypeScript `packages/session-format` for the existing ZIP/WAV encoding, validation, and sample-rate conversion. Both `apps/web` and the React frontend hosted by the Windows Tauri shell consume this same package outside audio processing. Keep React, device selection, Web Audio, Tauri, file dialogs/filesystem, IndexedDB/Web Locks, and `MessageChannel` scheduling out of the package. Hosts provide file access, recovery/storage coordination, cancellation/yield scheduling, and progress presentation. Preserve current session versions, validation/conversion behavior, and portable compatibility. Device IDs and Windows backend preferences stay in host settings, not session files. See [ADR-0012](../adr/0012-shared-session-format-package.md).

The Windows frontend transfers session manifests and bounded audio chunks to/from the native host through a separate acknowledged bulk-transfer path. The existing specs use at most 2,048 frames with one outstanding request; use that as a candidate until measured. Rust validates bounds, values, and engine invariants without duplicating the portable ZIP/WAV codec. Manual session import/export is in the planned Windows integration scope. Before committing the integration, measure IPC serialization/copy costs, peak temporary memory, cancellation and progress behavior, and UI responsiveness under load. Native recording snapshots and import staging must remain safe without file I/O or bulk transfer in the render callback. The precise ownership/lease or staging mechanism remains open for the native prototype.

Automatic Windows crash recovery and periodic recovery checkpoints are deferred until after the native audio prototype. They are outside prototype acceptance. Preserve a boundary for a future Windows recovery adapter, but do not build recovery infrastructure during the prototype. Revisit its priority for the first release after audio validation and session-transfer measurements; if deferred beyond that release, document that unsaved work cannot be restored after a crash. Existing Web recovery behavior remains unchanged. See [ADR-0013](../adr/0013-windows-recovery-deferral.md).

## Provisional native audio specification candidates — pending hardware validation

These are specification candidates, not confirmed release requirements. Validate them against the first reproducible hardware measurements, then confirm or revise the thresholds with the owner before finalizing the reviewed specification. Evaluate every hardware/endpoint configuration separately; never pool devices or assume the independently clocked configuration meets the targets before it is measured. Keep all agreed configurations in the validation scope and identify each one as meeting or missing the low-latency targets. Report complete physical microphone-to-output latency; requested or negotiated period duration and API-reported latency estimates are diagnostic context only. Windows documents pulse-based round-trip measurement and endpoint-dependent supported periods, but neither a small period nor an OS estimate proves this application's end-to-end latency ([Microsoft low-latency audio guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio), [IAudioClient3 shared periods](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getsharedmodeengineperiod)).

### Latency and Web comparison

- **Proposed low-latency target:** for each tested endpoint configuration and each workload (passthrough, one existing effect, representative two-track Loop/overdub), median complete mic-to-output latency is at or below 15 ms, p95 at or below 20 ms, and p99 at or below 30 ms. Report the effect's incremental latency separately. A setting/device that misses a gate is not called low-latency accepted even if it remains usable.
- **Proposed Web comparison goal (separate from native acceptance):** run the current Web app and native build on the same Windows machine, OS build, endpoints, driver versions, sample rate, channel routing, workload/effect and physical measurement fixture. Interleave Web/native trials to reduce order bias. For each configuration and workload, native p95's goal is both at least 30% and at least 5 ms lower than Web p95. Missing this comparative goal triggers review, but does not automatically fail a configuration that meets the native absolute latency and stability targets.
- **Proposed pulse plan:** use a fixed, externally generated, short broadband pulse/chirp sequence with 1,000 scheduled pulses per app/configuration/workload, distributed over three interleaved runs. Randomize pulse spacing within a pre-recorded 0.8–1.2 second interval so events do not synchronize with audio blocks; use the same sequence for Web and native. Record the scheduled and reference-detected pulse count. Report per-run results and the combined 1,000-pulse result for each individual app/configuration/workload; do not pool configurations.
- **Proposed measurement fixture:** use a calibrated, synchronized two-channel recorder at 96 kHz or higher. A reference microphone sits adjacent to the tested capture microphone to timestamp the acoustic stimulus; a fixed headphone coupler/microphone records the monitored output on the other channel. Document and keep fixed the source, placement, distances, output volume, and gain. Calibrate channel skew, the reference-microphone-to-device-microphone propagation offset, and coupler path delay; subtract only calibrated fixed fixture delay and report the correction. The residual expanded measurement uncertainty at 95% confidence should be no greater than 1 ms; otherwise improve the fixture or report the run as inconclusive. A suitable audio measurement fixture and owner-operated Windows hardware are required; screenshots of device settings are insufficient. A matched electrical loopback can be an additional diagnostic, but does not replace the acoustic microphone-to-output test for built-in and separate endpoints.
- **Proposed signal processing/statistics:** freeze the pulse detector and thresholds before collecting acceptance data. Detect each response by normalized cross-correlation against the known stimulus, with fixed predeclared search window and rejection threshold. For each matched event compute response timestamp minus reference timestamp minus calibrated fixture-path correction. Sort all valid event latencies and report nearest-rank median, p95, and p99 (`ceil(p*N)` in 1-based rank), plus min/max and a bootstrap 95% confidence interval for each percentile. Apply measurement uncertainty conservatively: the percentile's upper confidence bound plus the 95% expanded systematic uncertainty must remain within its proposed threshold.
- Every scheduled pulse must remain accounted for. If the reference channel confirms a stimulus but no valid output response is detected, count it as a missed response/dropout; do not remove it from the denominator or calculate a passing result from detected pulses alone. Any missed response makes that run fail the proposed zero-missed-pulse stability gate, while percentile values for detected responses may still be shown as diagnostic-only. A stimulus absent from the reference is a fixture/input failure; preserve the run and mark it invalid with the reason, then repeat the complete run. Never silently discard a glitch, outlier, invalid run, or failed measurement.

### Stability, synchronization, and load

- **Proposed duration:** run each matched-device configuration for 30 minutes in passthrough, with the selected effect, and under representative two-track playback/overdub load. Run each independently clocked separate-endpoint configuration for 60 minutes under representative load to expose drift. Repeat the UI/IPC stress run for at least 30 minutes on each configuration.
- **Proposed stability gate:** zero unexplained render underflows, capture overruns, lost/replaced frames, audio discontinuities, or audible dropouts during stable runs. Record buffer occupancy at least once per second; it must stay within configured bounds and show no sustained drift toward overflow/underflow. Record any clock correction and its amount. A buffer warning or adaptive resampling alone is not data loss. Confirmed capture loss during REC/overdub must trigger the specified interruption and is evaluated as a correct interruption case, not concealed or counted as a stable uninterrupted capture.
- During UI/IPC stress, keep audio running while repeatedly changing parameters, requesting snapshots/meters, and stalling or suspending WebView work for a proposed 30 seconds. The native audio callback must continue without a dropout. Saturated bounded queues must reject explicitly, preserve FIFO for accepted commands, and later report acceptance/application/supersession accurately; UI recovery must not replay stale-generation commands.
- Track command latency separately from monitoring latency, from adapter submission to engine-applied acknowledgement (queue acceptance alone does not stop the clock). Proposed target: p95 at or below 50 ms with a responsive UI and p99 at or below 250 ms during active IPC stress. During a deliberate WebView stall no UI-originated latency bound applies until the UI can submit again, but audio must continue and the first resumed command must follow the documented queue/generation rules.
- Test expected device-interruption behavior separately from stable-run accounting: induce a confirmed capture discontinuity during initial REC and overdub and verify the specified discarded/retained samples and session-wide UI notice; induce it in playback-only mode and verify playback continues with bounded recovery and diagnostics. These expected, correctly handled interruptions are not unexplained stability failures. Any unhandled loss, incorrect sample retention, silent concealment, or failure to report remains a test failure.

### Low-latency path versus fallback availability

Classify capture and render independently. A configuration counts toward low-latency acceptance only when both streams actually negotiated a supported low-period shared-mode setting and it meets the latency and stability gates. Record actual format, period, buffers, endpoint and driver for each stream. If either stream uses regular shared mode, label the run **fallback availability**; do not combine it with low-latency results or present a pass as evidence that the low-latency target was met.

**Proposed fallback availability check:** when low-period initialization is unsupported, regular shared mode starts and runs for 10 minutes without unreported stream failure, with accurate fallback reason/configuration diagnostics and correct device errors. This proves availability only. Device-busy, disconnected, and other initialization failures must remain distinct and must not be mislabeled as unsupported-period fallback. A low-period stream that glitches may retry a larger supported period only through the agreed controlled restart; record the retry and treat that new setting as a separate measured run.

### Owner-supplied hardware evidence

The owner needs to provide access to the Windows 11 x64 PC and perform the physical runs. Required matrix: matched duplex interface baseline; built-in microphone with wired headphones; USB microphone with built-in wired output; and at least one confirmed independently clocked capture/render pair for the 60-minute run. Treat each configuration as its own result and explicitly report whether it meets low-latency criteria; if no clock-independent pair can be identified, record how independence was established and leave that case unverified. Capture exact Windows build, PC, endpoint names, connection, device/driver versions, negotiated stream formats/periods/buffer sizes, fallback reason, effects/transport load, measurement fixture/calibration/uncertainty, scheduled/reference/matched/missed pulse counts, pulse data, invalid-run reasons, dropouts/discontinuities, and run duration. The agent can prepare commands, logging format, and analysis steps, but cannot claim the physical measurements without this owner-run evidence.

Tauri 2 is the selected initial Windows shell. It owns window management, local frontend hosting and application lifecycle; a Windows adapter translates the shared application contract at the entry point. Keep Tauri APIs and serialization in that shell/adapter. The WASAPI host and LoopEngine run on dedicated native audio threads, independent of Tauri handlers, async task scheduling and WebView responsiveness. Command acknowledgement must distinguish queue acceptance from engine application. Bounded/rate-limited snapshots and meters are delivered outside the callback; framework events/channels do not provide the application's queue bounds or acknowledgement semantics by themselves. Bundle frontend assets locally and check WebView2 Runtime availability during installation with an install/recovery path. Keep Web builds independent of Tauri and Windows tooling, and validate audio continuity under WebView stalls and heavy IPC traffic. See [ADR-0008](../adr/0008-tauri-windows-shell.md).
